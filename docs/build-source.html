This is a complete alternative to loading the prepared case files in the tutorial. It constructs the same decision, criteria, initial board, dossiers and review policy. All commands below run locally; no model calls occur during authoring. We supply public research and clearly labeled assumptions, then ask models to choose moves only after setup is complete.

Complete the tutorial’s installation first. With the virtual environment active, start in the package source folder and create a fresh game directory. If you already loaded the case elsewhere, leave that game in its own directory.

mkdir -p games/starbucks-authored
cd games/starbucks-authored

Define what Starbucks is considering

The question is whether protecting café capacity during the morning peak improves service without losing too much mobile business. We make it specific enough for a rival to respond: 50 pilot cafés, a 20% reservation, unchanged prices and three months of play. The $3 transaction contribution is our operating assumption, not a reported store margin.

{{BUILD_DECISION}}

game decision set starts a draft in .perla-design in this directory. Its fields describe the proposed experiment, including the monthly decision schedule. The response reports ready_to_initialize: false because we have not yet supplied evaluation criteria or the public situation. You can revise the decision by repeating this command before initialization.

Write the conditions that would make the pilot fail

A persuasive story about shorter queues is insufficient. We need observable conditions that would count against continuing the experiment. Each criterion therefore names a failure condition, what we would measure, a threshold and a deadline.

Service: enough improvement across enough stores

We propose a 20% reduction in the 90th-percentile café wait by February, after adjustment against comparison cafés. Requiring 40 complete pairs prevents a handful of favorable stores from carrying the conclusion.

{{BUILD_SERVICE}}

Economics: recover the labor cost across all channels

The pilot fails this test if incremental daily contribution remains negative by March. Count lost mobile purchases and transfers between channels as well as any new café business.

{{BUILD_ECONOMICS}}

Retention: keep the baseline mobile customers

A customer who buys at the counter still returns to Starbucks. Track repeat purchasing across its channels, and require complete follow-up for at least 1,000 customers in each arm.

{{BUILD_RETENTION}}

These thresholds are case-design choices. Missing evidence leaves a criterion unevaluated. To change an existing criterion before initialization, repeat its command with --replace; reusing its ID with different content otherwise fails.

Describe the shared starting situation

The board is the information every player can see at the start of a round. Here we establish the calendar, public participants, pilot scope and assumptions. We deliberately leave actual performance unmeasured: --unknown records a missing observation, while --number 0 records an observed-sample count of zero.

--text supplies prose, --number supplies a number, and --empty-list starts a list. append adds a text entry. A dotted field name such as period_ends.1 places the first round’s date inside the calendar schedule. The measurement rule tells control how to distinguish imagined developments from measured results.

{{BUILD_BOARD}}

For your own case, choose shared information deliberately. The private budgets and limits below belong in the corresponding player’s dossier. The shared board should not give competitors access to another player’s confidential plans.

Inspect the draft, then register it

game show displays the complete draft and any validation issues. At this point ready_to_initialize should be true. Read it before running the next command: initialization fixes the decision and criteria for this experiment.

{{BUILD_INITIALIZE}}

Without --input, init reads the local command-built draft. It creates the same .perla game record as initialization from a file. The draft remains available for inspection, but further design edits are refused once the game is initialized. A different proposal belongs in a fresh game directory.

The delegation flags allow this automated walkthrough to proceed without human sign-off on dossiers and rulings. For a facilitated exercise, omit them and follow the human-review procedure.

Build Starbucks: service, digital convenience and contribution

First register the company whose decision we are testing. Then give it sourced history and financial context, followed by explicit assumptions about authority, economics and information. Its management tension is concrete: improving café service can hurt mobile convenience, and added staff must earn back their cost.

A fact command records a claim under a stable ID and identifies its source. Incentives describe what the player wants; constraints limit its choices; capabilities identify what it can do; red lines state what it must not assume. A partial dossier stays a draft until it has sourced facts and all four kinds of strategy statements. Completing those fields makes it available for play; later entries enrich it.

{{BUILD_HOME}}

The h6 economics imply a $60 daily labor bill and 20 incremental transactions to cover it. That calculation can inform a move without prescribing one: the player can narrow the reservation window or release unused capacity within its authority. Read the background and sources as prose.

Build Dutch Bros: win a repeat visit without creating a queue

This player controls a local group of drive-through shops. Its acquisition budget makes an immediate response possible, while staffing and lane capacity make indiscriminate discounting costly. Its own order and redemption data cannot reveal who was rejected inside Starbucks’ app.

{{BUILD_DUTCH}}

These limits leave the player room to choose between staffing, acquisition and protecting service consistency. Read the full background and sources.

Build Dunkin: an offer the franchisees can sustain

The relevant decision maker coordinates consenting local restaurants. Its coffee-and-food basket creates a different offer from a beverage-only discount, but franchise economics constrain reimbursement, participation and promotion spending.

{{BUILD_DUNKIN}}

The constructed disagreement over traffic versus profitable food attachment gives the player a reason to care about the whole purchase. Read the full background and sources.

Build customers with somewhere else to go

The customer player represents three designed occasions, each with different time and spending limits. It receives public offers and its own experiences. Home preparation, postponement and no purchase remain possible, so a rejected mobile order need not become a competitor’s sale. These assumptions are not measured segment weights or customer testimony.

{{BUILD_BUYER}}

The time limits will influence the model’s responses. When an eight-minute tolerance appears again in a move, that is an input being applied. Read the complete situations and information limits.

Choose review settings and check readiness

Set the review policy directly. We allocate zero human reviews to escalated rulings for this automated exercise. The confidence threshold governs automatic eligibility of otherwise unflagged rulings based on dossier facts. The judgment-share threshold produces a warning when more than 40% of a closed round’s rulings rest on judgment. Player objections still run.

{{BUILD_POLICY}}

The status should report data.phase: move_generation and an empty missing_dossiers list. You have built the complete case without loading a JSON input file. The decision, criteria, board, four dossiers and policy match the tutorial’s supplied case; no model has chosen a move yet.
