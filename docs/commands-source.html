Recover execution without replacing accepted moves

A remote job is still running

ep run --background --wait can time out while a remote interview continues. Its JSON response includes a remote job UUID. Use that UUID to inspect or resume the same job. The placeholders below are values to replace with the actual UUID; they are not Perla’s internal job IDs.

ep jobs status REMOTE_JOB_UUID
ep jobs wait REMOTE_JOB_UUID --timeout 900 \
  --output round-1/moves/home.results.ep
# If the remote job has already completed:
ep jobs results REMOTE_JOB_UUID --output round-1/moves/home.results.ep

After a remote failure, inspect ep jobs errors REMOTE_JOB_UUID. Do not submit another paid job merely because the original one is slow. If there is no complete usable result, preserve the failure record before a fresh execution.

Perla rejects a completed response

Batch import identifies the Results file that failed. It commits none of the pending batch when one answer is missing or invalid. Keep valid files from the other actors. Preserve the rejected response and error, then rerun only that actor’s original ep command with --fresh and import the batch again.

# Example: only when Perla has rejected this file.
# Choose a new unused archive name for every rejected attempt.
mv round-1/moves/home.results.ep round-1/moves/home.rejected-1.results.ep

# Rerun the home ep command from the round above, then:
perla ingest moves --from round-1/moves

A structurally accepted move is immutable. Repeating a batch import skips jobs already accepted; it does not select the most attractive response. Keep the original export receipt and do not edit returned text to make it pass validation. Re-exporting a different batch requires a new directory.

Run with a facilitator’s review

At setup, initialize a fresh game without --delegate dossiers --delegate rulings, load the same cast and select case/policy.json, which budgets five reviews. After the facilitator has reviewed the actual dossiers, record that approval with their identity and explanation:

perla workflow approve dossiers --by FACILITATOR \
  --note 'Reviewed the dossier sources, authority, economics and information limits'

After final resolutions, perla adjudicate show --move 1 exposes the review routing. Obtain each required individual assessment, then record final approval. Substitute real ruling IDs and reasons from that review:

perla adjudicate assess --move 1 --ruling RULING_ID \
  --by FACILITATOR --note 'Specific assessment of this final ruling'
perla workflow approve rulings --move 1 --by FACILITATOR \
  --note 'Reason for approving the final round outcomes'
perla adjudicate close --move 1

These commands record a review that occurred; running them is not the review itself. If the reviewer finds a substantive problem, do not approve it merely to advance the round. Perla currently supports the single actor rebuttal/control resolution cycle, explicit board reconciliation and fresh scenario runs; it does not offer an unrestricted post-resolution ruling editor.

Resolve conflicting board fields

Two final rulings may propose different values for the same top-level board field. adjudicate show exposes the unresolved candidates, and closure refuses to choose silently. Prepare a JSON choices file naming one actual ruling for every conflicting field, with a reason. This is an example of the file structure; replace the field and ruling ID with the conflict in your run:

{
  "choices": {
    "calendar_period": {
      "ruling_id": "ACTUAL_RULING_ID",
      "reason": "This candidate uses the scheduled end of the current round."
    }
  }
}
perla adjudicate reconcile --move 1 --input choices.json --by FACILITATOR
perla adjudicate show --move 1

Reconciliation selects an existing proposed value; it cannot invent a replacement outcome. A materially unsuitable set of candidates is a reason to revisit the scenario rather than manufacture a clean closure.

Optionally record the criterion assessment

This stage follows three closed rounds. It was not executed in the original worked case. Complete the novelty baseline first so the final assessment can compare proposed insights with what an analyst could have anticipated from the initial inputs.

perla job generate novelty --output evaluation/novelty
ep run --jobs evaluation/novelty/scribe.jobs.ep \
  --model_list models/control.ep --background --wait --timeout 900 \
  --task-timeout 600 --remote_inference_results_visibility private \
  --output evaluation/novelty/scribe.results.ep
perla ingest novelty --from evaluation/novelty

perla job generate endgame --output evaluation/endgame
ep run --jobs evaluation/endgame/scribe.jobs.ep \
  --model_list models/control.ep --background --wait --timeout 900 \
  --task-timeout 600 --remote_inference_results_visibility private \
  --output evaluation/endgame/scribe.results.ep
perla ingest endgame --from evaluation/endgame
perla endgame show
perla workflow validate

Inspect missing evidence, insight ownership and prediction-resolution requirements before finalization. An unevaluated criterion is a legitimate assessment when the required observations are absent. perla endgame finalizes only after its completion gates are satisfied or explicit, attributed waivers are supplied; the assessment above does not silently finalize a report.
